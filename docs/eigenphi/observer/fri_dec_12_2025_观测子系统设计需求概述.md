## Pool State 的标识与有效性管理

### 状态规模
- 观测系统管理**数十万个** pool 状态

### StateId 的两种形式

#### StateId A:  `<blockNumber-txIndex>`
- **含义**：该状态在 `blockNumber` 这个 block 的第 `txIndex` 个 tx 执行后有效
- **有效期**：从该 tx 后开始，直到被更新的 state 替代
- **对应功能**：功能1（已上链的确定性状态）

#### StateId B: `<blockNumber-pendingTxHashList>`
- **含义**：在 `blockNumber` 的 block 末尾，按顺序执行一组 `pendingTxList` 后，这组状态才有效
- **有效性条件**：
  - pendingTxList 中的 tx 按顺序上链
  - 在 blockNumber 与 pendingTx 之间没有插入其他与 pool 有关的交易
- **失效条件**：
  1. pendingTx 上链了（变成确定性状态）
  2. 在 blockNumber 与 pendingTx 之间插入了其他与 pool 有关的交易
- **对应功能**：功能2（条件性/预测性状态）

## 观测状态的利用与有效性约束

### 功能1观测到的 Onchain State 约束

#### 原子性特征
- 一批 state 是原子的：**要么全生效，要么全不生效**
- 不能部分生效

#### Blockchain Reorg 处理
- **正确处理流程**：
  1. 先将无效 block 的状态置为无效
  2. 再重新获取正确 block 的 pool 状态
- **错误处理**：单独更新部分 state（会破坏原子性）

### 功能2观测到的 Pending State 约束

#### 整体性特征
- 依赖某组 pendingTx 的 pool state 是一个**整体**
- **不能只更改其中的一部分**
- 例如：如果 3 个 pool 的 state 都依赖 pendingTxList，那么这 3 个 pool 的 state 必须作为一个整体存在或失效

## 我的理解确认：

### 关于原子性/整体性的理解

1. **功能1的原子性**：
   - 场景：在 block N 中，一个 tx 可能影响多个 pool
   - 约束：这些 pool 的 state 必须作为一个原子单元
   - 原因：它们来自同一个已确认的链上执行

2. **功能2的整体性**：
   - 场景：一组 pendingTxList 可能影响多个 pool
   - 约束：这些 pool 的 state 必须作为一个整体
   - 原因：它们基于同一个"假设执行路径"

3. **Reorg 的复杂性**：
   - 需要批量失效一批 state
   - 需要批量重新获取新的 state
   - 不能出现"部分旧 state + 部分新 state"的混合情况

### 关于下游使用的理解

4. **下游计算子系统的使用场景**：
   - 下游需要基于一致的 state 集合进行套利计算
   - 如果 state 不一致（部分是旧的，部分是新的），会导致计算出错误的套利机会

## 关键技术点

### 1. Reth 内部组件：Pool State Tracker

**职责**：
- 在 block 执行后，识别所有 pool 相关的 logs
- 批量获取这些 pool 的 raw state
- 触发转换和验证流程

**实现要点**：

```rust
// 伪代码

pub struct PoolStateTracker {
    // 已知的 pool 地址和协议类型映射
    pool_registry: HashMap<Address, ProtocolType>,
    
    // Raw state 获取器（批量调用合约）
    state_fetcher: RawStateFetcher,
    
    // 转换器和验证器
    converter: StateConverter,
    validator:  StateValidator,
    
    // 缓存
    cache: Arc<RwLock<VerifiedStateCache>>,
}

impl PoolStateTracker {
    /// 在 block 执行完成后调用
    pub fn on_block_executed(&self, block:  &Block, receipts: &[Receipt]) -> Result<Vec<VerifiedPoolState>> {
        // 1. 从 receipts 中提取 pool 相关的 logs
        let pool_events = self.extract_pool_events(receipts)?;
        
        // 2. 识别需要更新 state 的 pools
        let affected_pools:  HashSet<Address> = pool_events.iter()
            .map(|event| event.pool_address)
            .collect();
        
        // 3. 批量获取 raw state (关键：本地调用，无需跨进程 IO)
        let raw_states = self.state_fetcher.batch_fetch(
            &affected_pools,
            block.number,
            block.hash
        )?;
        
        // 4. 转换为 constraints state
        let constraints_states = raw_states.iter()
            .map(|raw| self.converter.convert(raw))
            .collect::<Result<Vec<_>>>()?;
        
        // 5. 验证 (关键：本地模拟，无需跨进程 IO)
        let verified_states = constraints_states.iter()
            .map(|state| self.validator.validate(state, block.number))
            .collect::<Result<Vec<_>>>()?;
        
        // 6. 写入缓存
        for state in &verified_states {
            self. cache.write().insert(state.clone());
        }
        
        Ok(verified_states)
    }
    
    /// 识别 pool 相关的 logs
    fn extract_pool_events(&self, receipts: &[Receipt]) -> Result<Vec<PoolEvent>> {
        let mut events = Vec::new();
        
        for (tx_index, receipt) in receipts.iter().enumerate() {
            for log in &receipt.logs {
                // 检查是否是已知 pool 的事件
                if let Some(protocol) = self.pool_registry. get(&log.address) {
                    // 根据 protocol 类型解析 event
                    match protocol {
                        ProtocolType::UniswapV2 => {
                            if log.topics[0] == UNISWAP_V2_SYNC_EVENT_SIGNATURE {
                                events.push(self.parse_uniswap_v2_sync(log, tx_index)?);
                            }
                        },
                        ProtocolType:: UniswapV3 => {
                            if log.topics[0] == UNISWAP_V3_SWAP_EVENT_SIGNATURE {
                                events.push(self.parse_uniswap_v3_swap(log, tx_index)?);
                            }
                        },
                        // ...  其他协议
                    }
                }
            }
        }
        
        Ok(events)
    }
}
```

**关键优化点**：
- `batch_fetch`：批量调用，避免多次 IO
- 所有操作在 reth 进程内完成，避免序列化/反序列化
- 利用 reth 的 EVM 实例，无需启动新的执行环境

```rust
        // 1. 生成测试 swap 参数

        // 3. 本地数值计算
        let local_result = self.calculator.calculate_swap(state, &test_swap)?;
        
        // 4. 对比误差
        let error = self. calculate_error(&onchain_result, &local_result);
        
        if error <= self.error_threshold {
            Ok(VerifiedPoolState {
                state: state.clone(),
                validated_at: format!("{}-{}", block_number, state.tx_index),
                validation_error: None,
            })
        } else {
            // 验证失败，标记为不可计算
            Ok(VerifiedPoolState {
                state: state.clone(),
                validated_at: format!("{}-{}", block_number, state.tx_index),
                validation_error: Some(format!("Error {} exceeds threshold {}", error, self.error_threshold)),
            })
        }
    }
}
```

**关键决策点（需要您确认）**：

❓ **问题 A**：State Converter 是否需要在 Reth 内实现？
- 如果转换逻辑复杂且频繁变化，可能更适合在观测系统中实现
- 但如果转换逻辑稳定，放在 Reth 内可以减少数据传输量

我的建议：
- **阶段1**：Reth 只返回 raw state，转换在观测系统完成（快速迭代）
- **阶段2**：转换逻辑稳定后，迁移到 Reth 内（性能优化）

❓ **问题 B**：Validator 是否必须 100% 验证？
- 如果验证失败率 < 1%，建议采用**抽样验证**（如 10% 采样率）
- 对于高价值 pool（如 WETH/USDC），100% 验证
- 对于低价值 pool，抽样验证

我的建议：**分级验证策略**

### 3. Reth 内部组件：Verified State Cache

**职责**：
- 缓存验证后的 pool states
- 处理 reorg 时的批量失效
- 提供快速查询接口

**实现要点**：

```rust
pub struct VerifiedStateCache {
    // 按 blockNumber 索引 (用于 reorg 批量失效)
    by_block: BTreeMap<u64, HashMap<Address, VerifiedPoolState>>,
    
    // 按 poolAddress 索引 (用于快速查询最新 state)
    by_pool: HashMap<Address, BTreeMap<StateId, VerifiedPoolState>>,
    
    // Pending states (依赖 pending tx 的 states)
    pending_states: HashMap<H256, Vec<VerifiedPoolState>>,  // pendingTxHash -> states
}

impl VerifiedStateCache {
    /// 插入新的 verified state
    pub fn insert(&mut self, state: VerifiedPoolState) {
        let block_number = state.state_id.block_number;
        let pool_address = state.state. pool_address;
        
        // 插入到 by_block 索引
        self.by_block
            .entry(block_number)
            .or_insert_with(HashMap::new)
            .insert(pool_address, state. clone());
        
        // 插入到 by_pool 索引
        self.by_pool
            .entry(pool_address)
            .or_insert_with(BTreeMap::new)
            .insert(state.state_id. clone(), state);
    }
    
    /// 处理 reorg：批量失效指定 blocks 的所有 states
    pub fn invalidate_blocks(&mut self, invalid_blocks: &[u64]) {
        for block_number in invalid_blocks {
            // 从 by_block 索引中移除
            if let Some(states) = self.by_block.remove(block_number) {
                // 从 by_pool 索引中移除对应的 states
                for (pool_address, state) in states {
                    if let Some(pool_states) = self.by_pool.get_mut(&pool_address) {
                        pool_states.remove(&state. state_id);
                    }
                }
            }
        }
    }
    
    /// 查询指定 pool 在指定 block 的最新 state
    pub fn get_latest_state(&self, pool_address: &Address, block_number:  u64) -> Option<&VerifiedPoolState> {
        self.by_pool
            .get(pool_address)?
            .range(..=StateId::new(block_number, u32::MAX))
            .next_back()
            .map(|(_, state)| state)
    }
}
```

**关键优化**：
- 使用双索引（by_block + by_pool）支持不同查询场景
- Reorg 时批量失效，保证原子性
- 使用 BTreeMap 支持范围查询（查询某个 block 之前的最新 state）

## 第一部分：需求确认与业务约束

### 1.1 业务需求确认

#### 核心业务目标
利用 ETH 链上 pool 之间的价差实现无风险套利，要求观测系统提供**全面、准确、快速**的 pool state 数据。

#### 三大评价指标

**1. 全（完整性）**
- **定义**：观测到所有应该观测的 pool state，无误报、无漏报
- **业务约束**：
  - Pool 范围动态变化（通过 Factory 不断创建新 pool）
  - 必须自动发现新创建的 pool
  - 系统初始化时可从旧系统导入已知 pool

**2. 准（准确性）**
- **定义**：准确观测 pool state，包括区块位置准确、状态记录和转换正确
- **业务约束**：
  - State 必须关联正确的 `<blockNumber-txIndex>` 或 `<blockNumber-pendingTxHashList>`
  - Raw state → Constraints state 转换必须准确
  - **100% 验证是强制性要求**（验证失败率 60%+ 是正常的，因为下游只能计算特定类型的 state）

**3. 快（低延迟）**
- **定义**：在主要用户请求场景中，pool state 以最快速度返回给下游
- **业务约束**：
  - Onchain state：期望 1 秒内完成从 block 产生到验证完成的全流程
  - Pending tx 模拟：期望 10ms 级完成（否则 tx 可能已上链，模拟失效）

### 1.2 关键业务约束

#### 约束 1：State 的原子性
- 同一 block 或同一组 pendingTxList 影响的所有 pool state 必须作为原子单元
- Reorg 时必须批量失效，不能部分更新

#### 约束 2：验证的强制性
- **100% 验证是不可妥协的条件**
- 验证失败的 pool 必须标记为"不可计算"并通知观测系统
- 验证失败率高（60%+）是正常的业务现象

#### 约束 3：优先级
- Onchain state 优先于 pending tx state
- Pending tx state 必须基于已确认的 onchain state 进行模拟

#### 约束 4：状态规模
- 需要管理数十万个 pool state
- 单个 block 可能影响数百到上千个 pool

```
│  │         ↓                                            │    │
│  │  调用 eth_callSimulate 模拟执行                    │    │
│  │         ↓                                            │    │
│  │  解析 logs 识别受影响的 pool                       │    │
│  │         ↓                                            │    │
│  │  调用 eth_callSimulate 获取 raw state              │    │
│  │         ↓                                            │    │
│  │  转换 + 验证                                        │    │
│  └─────────────────────────────────────────────────────┘    │
│                                                               │
└───────────────────┬───────────────────────────────────────────┘
                    │ 多次 eth_callSimulate (IO 瓶颈)
                    │
┌───────────────────▼───────────────────────────────────────────┐
│                    Geth 节点                                   │
│  - 自定义 eth_callSimulate API                                │
│  - 在 pending block 上模拟执行                                │
└────────────────────────────────────────────────────────────────┘
```

### 2.2 核心性能瓶颈

#### 瓶颈 1：多次跨进程 IO
```
功能1 IO 路径：
观测系统 → Geth (获取 raw state, 500ms-2s)
观测系统 → Geth (验证 swap, 再次耗时)

功能2 IO 路径：
观测系统 → Geth (模拟 pending tx)
观测系统 → Geth (获取 raw state)
观测系统 → Geth (验证 swap)
```

**问题根源**：
- 每次 `eth_callSimulate` 都需要跨进程通信（IPC/HTTP/WebSocket）
- 数据需要序列化/反序列化
- 取 5 个 UniswapV3 pool state 耗时 500ms-2s，远超业务目标（1 秒内完成全流程）

#### 瓶颈 2：被动等待推送
- WebSocket 推送 eventlog 的延迟不可控
- 无法主动控制数据获取的优先级和批量度

#### 瓶颈 3：重复计算
- 获取 raw state 和验证 swap 都需要访问同一个 pool 的 storage
- 但由于跨进程调用，无法复用 EVM 状态

### 2.3 现有系统的正确设计

尽管存在性能瓶颈，现有系统的以下设计是正确的：

✅ **EventLog 过滤机制**：通过监听 Sync/Swap 事件识别变化的 pool，避免盲目轮询

✅ **100% 验证策略**：通过对比链上模拟和本地计算确保数据准确性

✅ **StateId 管理**：通过 `<blockNumber-txIndex>` 和 `<blockNumber-pendingTxHashList>` 明确 state 的有效性条件

✅ **原子性保证**：Reorg 时批量失效 state

## 第三部分：核心技术选型

### 3.1 关键技术决策：为什么选择 Reth ExEx？

#### 技术决策点：状态获取的位置

我们有三种技术选项：

##### 选项 A：在观测系统中通过 RPC 获取（现状）
```
观测系统 --RPC--> Reth --EVM 执行--> 返回结果
```
- ❌ 跨进程 IO，延迟高（500ms-2s）
- ❌ 无法复用 EVM 状态
- ❌ 无法控制执行优先级

##### 选项 B：在 Reth 核心中添加 Hook
```
Reth 核心 --执行 block--> Hook 拦截 --> 获取 pool state --> 推送
```
- ✅ 减少跨进程 IO
- ❌ 侵入 Reth 核心代码，升级维护成本高
- ❌ 与区块执行流程耦合，可能阻塞主流程

##### 选项 C：使用 Reth ExEx (推荐)
```
Reth 核心 --执行 block--> ExEx 订阅 --> 直接访问 storage --> 推送
```
- ✅ 不侵入 Reth 核心，独立进程/线程
- ✅ 可以直接访问 state database
- ✅ 不阻塞区块执行流程
- ✅ Reth 官方推荐的扩展机制
- ✅ 便于测试和迭代

#### 决策结果：选择 Reth ExEx

**理由**：
1. **性能优势**：ExEx 可以直接读取 contract storage，无需通过 RPC/IPC
2. **架构优势**：ExEx 是独立的执行单元，不阻塞区块处理
3. **维护优势**：ExEx 是 Reth 的官方扩展机制，升级兼容性好
4. **学习曲线**：适合初学者，有清晰的文档和示例

### 3.2 技术可行性验证

#### 问题：能否通过直接读 storage 获取 pool state？

**需要验证的关键点**：

##### 验证点 1：UniswapV2 Pool State 读取

UniswapV2 需要读取的 state：
```solidity
// UniswapV2Pair 合约
uint112 private reserve0;           // Slot 8 的前 112 位
uint112 private reserve1;           // Slot 8 的中间 112 位
uint32  private blockTimestampLast; // Slot 8 的后 32 位
```

**可行性**：✅ 可行
- 只需读取 1 个 storage slot (slot 8)
- 解析方式明确（固定布局）

##### 验证点 2：UniswapV3 Pool State 读取

UniswapV3 需要读取的 state：
```solidity
// UniswapV3Pool 合约

    uint160 sqrtPriceX96;
    int24 tick;
    uint16 observationIndex;
    uint16 observationCardinality;
    uint16 observationCardinalityNext;
    uint8 feeProtocol;
    bool unlocked;
}
Slot0 public slot0;  // Slot 0

uint128 public liquidity;  // Slot 1

mapping(int16 => uint256) public tickBitmap;  // Slot 5
mapping(int24 => Tick. Info) public ticks;     // Slot 6
```

**可行性**：⚠️ 部分可行，需要优化策略
- `slot0` 和 `liquidity`：✅ 只需读取 2 个固定 slot
- `tickBitmap` 和 `ticks`：⚠️ 是 mapping，需要计算 slot hash
  - 问题：不知道哪些 tick 是活跃的，可能需要读取大量 slot
  - 解决方案：
    - **方案 1**：通过事件 log 识别活跃的 tick 范围，只读取活跃范围
    - **方案 2**：维护活跃 tick 的索引（在 ExEx 中逐步构建）
    - **方案 3**：第一次通过 RPC 调用 `ticks()` 获取全量，后续增量更新

##### 验证点 3：UniswapV4 Pool State 读取

UniswapV4 使用 PoolKey + PoolManager 架构，state 读取方式不同：
```solidity
// PoolManager 合约
mapping(PoolId => Pool. State) public pools;
```

**可行性**：⚠️ 需要深入研究
- PoolId 是通过 PoolKey hash 计算的
- Pool.State 的 storage 布局需要分析

**首席架构师的判断**：
- UniswapV2：✅ 完全可行，无风险
- UniswapV3：⚠️ 可行但需要优化策略，建议分阶段实施
  - 阶段 1：只读取 `slot0` 和 `liquidity`（核心数据）
  - 阶段 2：实现 tick 数据的增量更新
- UniswapV4：⚠️ 需要进一步技术调研，不阻塞 V2/V3 的实施

#### 验证点 4：Storage 读取性能

**需要实验验证**：
- 单个 storage slot 读取延迟：预期 <1μs（内存操作）
- 批量读取 1000 个 slot 的延迟：预期 <1ms
- 对比 `eth_callSimulate`（500ms-2s）：提升 500-2000 倍

**验证方法**：
```
实验1：在 Reth ExEx 中读取 100 个 UniswapV2 pool 的 reserves
  - 测量总延迟
  - 验证数据正确性

实验2：在 Reth ExEx 中读取 100 个 UniswapV3 pool 的 slot0
  - 测量总延迟
  - 验证数据正确性

实验3：对比 eth_callSimulate 获取相同数据的延迟
```

### 4.2 架构设计原则

#### 原则 1：数据就近处理
- Pool state 的获取、转换、验证全部在 Reth ExEx 中完成
- 观测系统只接收最终的 verified state，无需再次处理

#### 原则 2：单次推送
- 一个 block 的所有 verified states 作为原子单元一次性推送
- 消除多次 IO 往返

#### 原则 3：存储直读
- ExEx 直接读取 contract storage，绕过 EVM 调用开销
- 对于复杂的 storage 布局（如 UniswapV3 ticks），采用增量更新策略

#### 原则 4：异步非阻塞
- ExEx 独立于 Reth Core 执行，不阻塞区块处理
- 如果 pool state 处理速度跟不上出块速度，采用队列缓冲

#### 原则 5：可验证的迭代
- 分阶段实施，每个阶段都可以独立验证正确性
- 适合团队没有 Rust 工程师的情况（与 AI 协作编码）

```
  ↓
```

#### 关键设计点

**设计点 1：支持的 Factory 合约**
- UniswapV2: 主网地址 `0x5C69bEe701ef814a2B6a3EDD4B1652CB9cc5aA6f`
- UniswapV3: 主网地址 `0x1F98431c8aD98523631AE4a59f267346ea31F984`

### 5.2 组件 2：Pool State Tracker

#### 职责
- 监听区块执行完成事件
- 从 logs 中识别发生变化的 pool
- 批量读取这些 pool 的 raw state (直接访问 storage)
- 将 raw state 传递给 State Converter

#### 数据流设计

```
ExEx 收到区块执行完成通知
  ↓
提取区块中的所有 logs
  ↓
识别 pool 相关事件
  ├─ UniswapV2: Sync(reserve0, reserve1)
  ├─ UniswapV3: Swap(... ), Mint(...), Burn(...)
  └─ UniswapV4: Swap(...), ModifyPosition(...)
  ↓
构建 "需要更新的 pool 列表"
  - pool_address
  - tx_index (用于生成 StateId)
  ↓
批量读取 pool state (直接读 storage)
  ↓
  对于 UniswapV2: 
    - 读取 slot 8 (reserve0, reserve1, blockTimestampLast)
  ↓
  对于 UniswapV3:
    - 读取 slot 0 (slot0)
    - 读取 slot 1 (liquidity)
    - 读取活跃 tick 范围的 tickBitmap 和 ticks (增量更新)
  ↓
将 raw state 传递给 State Converter
```

#### 核心技术：直接读取 Storage

**UniswapV2 Pool State 读取**

```
Storage Layout (Solidity):
  slot 8: reserve0 (uint112) | reserve1 (uint112) | blockTimestampLast (uint32)

读取方法: 
  1. 获取 pool 合约的 AccountState
  2. 读取 storage slot 8
  3. 解析: 
     - reserve0 = slot_value & ((1 << 112) - 1)
     - reserve1 = (slot_value >> 112) & ((1 << 112) - 1)
     - blockTimestampLast = (slot_value >> 224) & ((1 << 32) - 1)

伪代码:
  let storage_value = state_db.get_storage(pool_address, U256::from(8))?;
  let reserve0 = storage_value. as_u128() & ((1u128 << 112) - 1);
  let reserve1 = (storage_value.as_u128() >> 112) & ((1u128 << 112) - 1);
  let timestamp = (storage_value.as_u128() >> 224) as u32;
```

**UniswapV3 Pool State 读取（分阶段）**

```
阶段 1: 只读取核心数据 (slot0 + liquidity)
  - slot 0: slot0 结构体
  - slot 1: liquidity
  
  这已经足够进行基本的价格计算和验证

阶段 2: 增量更新 tick 数据
  - 维护每个 pool 的 "活跃 tick 范围"
  - 当 Swap/Mint/Burn 事件触及新的 tick 时，读取对应的 tickBitmap 和 ticks
  - 使用 LRU cache 缓存常用 tick 数据

阶段 3: 全量 tick 数据 (可选)
  - 如果下游计算子系统需要完整的 tick 数据，再实现全量读取
```

#### 批量读取优化

```
问题:  单个 block 可能影响 100+ 个 pool，如何高效读取？

策略 1: 批量读取同一类型的 pool
  - 将 pool 按协议类型分组
  - 同类型的 pool storage layout 相同，可以批量处理
  
策略 2: 并行读取 (可选)
  - 使用 Rayon 或 Tokio 并行读取不同 pool 的 storage
  - 注意:  需要确保 state_db 支持并发读取

策略 3: 缓存复用
  - 对于连续多个 block 都没有变化的 pool，无需重复读取
  - 维护 "上次读取的 block number"，只读取变化的 pool
```

#### 关键设计点

**设计点 1：如何访问 State Database？**

Reth ExEx 提供的接口: 
```rust
// ExEx 可以访问的上下文
pub struct ExExContext {
    pub provider: StateProviderFactory,  // 可以查询 state
    // ... 
}

// 使用方法

let account = state.basic_account(pool_address)?;  // 获取账户
let storage = state.storage(pool_address, slot)?;  // 读取 storage
```

**设计点 2：如何识别活跃的 tick (UniswapV3)？**

方案 A: 从事件 log 中推断
```
Swap 事件包含 tick 参数，表示当前价格所在的 tick
Mint/Burn 事件包含 tickLower 和 tickUpper

策略：
- 维护每个 pool 的 "当前 tick" 和 "活跃 tick 集合"
- 每次事件触发时，更新活跃 tick 集合
- 只读取活跃 tick 范围内的 tickBitmap 和 ticks
```

方案 B: 增量构建 tick 索引
```
首次观测某个 pool 时: 
- 通过 RPC 调用获取当前 tick 附近的 tick 数据
- 写入本地 cache

后续观测:
- 只读取新触及的 tick 数据
- 增量更新 cache
```

推荐：**方案 A + 方案 B 结合**

**设计点 3：错误处理**

如果读取 storage 失败（如 pool 合约被自毁、storage 布局变化）：
- 记录错误日志
- 标记该 pool 为 "不可计算"
- 继续处理其他 pool（不中断整个流程）

### 5.3 组件 3：State Converter

#### 职责
- 将 raw state 转换为 constraints state
- 支持多协议 (UniswapV2/V3/V4)
- 插件化设计，便于扩展新协议

#### 接口设计

```
Trait 定义: 

┌─────────────────────────────────────────────────────────────┐
│  pub trait ProtocolConverter:  Send + Sync {                 │
│      /// 协议类型                                            │
│      fn protocol_type(&self) -> ProtocolType;               │
│                                                              │
│      /// 将 raw state 转换为 constraints state              │
│      fn convert(                                             │
│          &self,                                              │
│          pool:  &PoolMetadata,                               │
│          raw_state:  RawPoolState,                           │
│          block_number: u64,                                 │
│          tx_index: u32,                                     │
│      ) -> Result<ConstraintsState>;                         │
│  }                                                           │
└─────────────────────────────────────────────────────────────┘

数据结构: 

RawPoolState (原始状态):
  - UniswapV2: { reserve0: u128, reserve1: u128, timestamp: u32 }
  - UniswapV3: { sqrtPriceX96: U256, liquidity: u128, tick: i32, ...  }
  - UniswapV4: { ...  }

ConstraintsState (约束状态):
  - 业务定义的"价格曲线函数"
  - 具体格式由下游计算子系统定义
  - State Converter 负责实现转换逻辑
```

#### 实现示例：UniswapV2Converter

```
转换逻辑 (概念):

输入:
  - reserve0: u128
  - reserve1: u128
  - token0: Address
  - token1: Address

输出 (constraints state):
  - 常数乘积约束:  reserve0 * reserve1 = k
  - 价格函数: price = reserve1 / reserve0
  - Swap 计算函数: amountOut = getAmountOut(amountIn, reserveIn, reserveOut)

伪代码:
  pub fn convert(raw:  RawV2State) -> ConstraintsState {
      let k = U256::from(raw.reserve0) * U256::from(raw.reserve1);
      
      ConstraintsState:: UniswapV2 {
          reserve0: raw.reserve0,
          reserve1: raw.reserve1,
          k:  k,
          fee: 30,  // 0.3% fee
          // 下游可以用这些数据计算 swap 结果
      }
  }
```

#### 实现示例：UniswapV3Converter

```
转换逻辑 (概念):

输入:
  - sqrtPriceX96: U256
  - liquidity: u128
  - tick: i32
  - fee: u32
  - (可选) ticks 数据

输出 (constraints state):
  - 当前价格: price = (sqrtPriceX96 / 2^96)^2
  - 流动性: liquidity
  - 价格曲线函数: 基于 x*y=L^2 在 tick 范围内的分段函数
  - Swap 计算函数: 考虑 tick crossing 的复杂逻辑

伪代码: 
  pub fn convert(raw: RawV3State) -> ConstraintsState {
      let price = calculate_price_from_sqrt(raw.sqrtPriceX96);
      
      ConstraintsState::UniswapV3 {
          sqrtPriceX96: raw.sqrtPriceX96,
          liquidity: raw.liquidity,
          tick: raw.tick,
          fee: raw.fee,
          // 如果有 ticks 数据，也包含进来
          active_ticks: raw.active_ticks,
      }
  }
```

#### 关键设计点

**设计点 1：转换逻辑的正确性验证**

问题: 转换算法可能有 bug，导致 constraints state 不准确

策略: 
- **单元测试**: 对每个 Converter 编写单元测试，使用已知的 raw state 和预期的 constraints state 对比
- **集成测试**:  在 ExEx 中转换真实的 pool state，然后用 State Validator 验证
- **对比测试**: 与旧系统的转换结果对比（如果旧系统的转换是正确的）

**设计点 2：转换逻辑的变更管理**

问题: 下游计算子系统可能升级算法，需要不同的 constraints state 格式

策略:
- **版本化**: ConstraintsState 包含 `version` 字段
- **兼容性**:  Converter 支持输出多个版本的 constraints state
- **灰度切换**: 下游可以同时接收旧版本和新版本，逐步切换

**设计点 3：性能优化**

转换是纯计算，预期延迟 <1ms/pool，但仍需注意: 
- 避免不必要的大整数运算
- 复用计算结果 (如 sqrtPriceX96 -> price 的转换)

### 5.4 组件 4：State Validator

#### 职责
- 验证 constraints state 的正确性
- 模拟特定金额的 swap，对比链上结果和本地计算结果
- 100% 验证所有 state
- 标记验证失败的 pool 为"不可计算"

#### 验证流程设计

```
输入:
  - constraints_state: ConstraintsState
  - pool_metadata: PoolMetadata
  - block_number: u64
  - tx_index: u32

步骤 1: 生成测试 swap 参数
  - 根据 pool 的流动性大小，选择合适的 swap 金额
  - 例如: amountIn = liquidity * 0.01 (1% 的流动性)
  - 方向: token0 -> token1

步骤 2: 链上模拟 swap
  - 调用 EVM 模拟执行 swap 交易
  - 记录 amountOut (链上结果)

步骤 3: 本地计算 swap
  - 使用 constraints_state 进行数值计算
  - 记录 amountOut (本地结果)

步骤 4: 对比误差
  - error = |amountOut_链上 - amountOut_本地| / amountOut_链上
  - 如果 error <= threshold (如 0.0001 = 0.01%)
      -> 验证通过
  - 否则
      -> 验证失败，标记为"不可计算"

输出:
  - VerifiedPoolState {
      state: constraints_state,
      state_id: "<blockNumber>-<txIndex>",
      validation_status: Pass | Fail,
      validation_error: Option<f64>,  // 误差百分比
    }
```

#### 关键技术：如何在 ExEx 中模拟 Swap？

**方案 A：调用 Reth 的 EVM (推荐)**

```rust
// ExEx 中可以访问 Reth 的 EVM 执行器

// 伪代码
let evm = Evm::builder()
    .with_db(state_provider)  // 使用当前 block 的 state
    .build();

// 构造 swap 交易
let swap_tx = TransactionRequest {
    from:  VALIDATOR_ADDRESS,  // 预设的测试地址
    to: pool_address,
    data: encode_swap_call(amount_in, ... ),  // ABI 编码
    value: U256:: ZERO,
};

// 模拟执行
let result = evm.transact(swap_tx)?;

// 解析返回值
let amount_out = decode_swap_result(result. output)?;
```

**优势**:
- 无需跨进程 IO，延迟 <1ms
- 使用与 Reth Core 相同的 EVM，保证一致性

**方案 B：直接读取 pool 合约代码并执行 (复杂度高，不推荐)**

**决策**: 采用方案 A

#### 本地计算 Swap 的实现

**UniswapV2 Swap 计算**

```
公式: 
  amountOut = (amountIn * 997 * reserveOut) / (reserveIn * 1000 + amountIn * 997)

伪代码:
  pub fn calculate_swap_v2(
      state: &ConstraintsStateV2,
      amount_in: u128,
  ) -> u128 {
      let amount_in_with_fee = amount_in * 997;
      let numerator = amount_in_with_fee * state.reserve1;
      let denominator = state.reserve0 * 1000 + amount_in_with_fee;
      (numerator / denominator) as u128
  }
```

**UniswapV3 Swap 计算**

```
复杂度:
  - 需要考虑 tick crossing
  - 需要考虑 tick 范围内的流动性变化
  - 计算公式涉及 sqrtPriceX96 的更新

建议:
  - 如果下游计算子系统已经实现了 V3 swap 计算逻辑，直接复用
  - 否则，参考 Uniswap V3 官方的数学公式实现

注意: 
  - 这里的计算精度非常重要，需要使用高精度整数运算
  - Rust 可以使用 `ethnum` 或 `uint` crate
```

#### 验证阈值的设置

```
问题: 阈值设置多少合适？

考量:
  - 太小 (如 0.0001%)：可能因为舍入误差导致大量误报
  - 太大 (如 1%)：可能遗漏真正的错误

建议:
  - 初始阈值:  0.01% (万分之一)
  - 根据实际验证失败率动态调整
  - 不同协议可以设置不同的阈值

配置:
  - 通过配置文件设置，便于调整
  - 支持按 protocol 和 pool 粒度配置
```

#### 关键设计点

**设计点 1：验证失败率 60%+ 的处理**

您提到验证失败率 60%+ 是正常的，因为下游只能计算特定类型的 state。

问题: 哪些 state 是"不可计算"的？

猜测：
- Pool 流动性太低（导致 slippage 过大）
- Pool 使用了特殊的费率结构
- Pool 是非标准实现（如分叉版本）

策略:
- 验证失败的 pool，在推送时标记 `validation_status: Fail`
- 下游可以选择忽略这些 pool，或者用其他方式处理
- 记录验证失败的原因（如误差值），便于分析

**设计点 2：验证性能优化**

100% 验证意味着每个 pool 都要模拟一次 swap，如果单个 block 影响 1000 个 pool，总延迟可能达到 1000ms。

优化策略：
- **并行验证**: 使用 Rayon 或 Tokio 并行验证多个 pool
- **批量模拟**: 如果 EVM 支持，可以在一个交易中批量调用多个 pool 的 swap（减少 EVM 初始化开销）
- **缓存验证结果**: 对于连续多个 block 都没有变化的 pool，无需重复验证

**设计点 3：验证失败后的处理**

验证失败的 pool 是否需要重试？

建议：
- 不重试（因为 60%+ 失败率表明这是业务正常现象）
- 标记为"不可计算"并推送给下游
- 下游可以自行决定是否使用这些 state

### 5.5 组件 5：Verified State Cache

#### 职责
- 缓存验证后的 pool state
- 支持快速查询（按 pool、按 block、按 stateId）
- 处理 reorg 时的批量失效
- 提供持久化支持（可选）

#### 数据结构设计

```
核心数据结构: 

┌─────────────────────────────────────────────────────────────┐
│  VerifiedPoolState                                           │
├─────────────────────────────────────────────────────────────┤
│  - pool_address: Address                                     │
│  - protocol:  ProtocolType                                    │
│  - state_id:  StateId                                         │
│  - constraints_state: ConstraintsState                       │
│  - validation_status: ValidationStatus                       │
│  - validation_error: Option<f64>                             │
│  - created_at: u64  // timestamp                             │
└─────────────────────────────────────────────────────────────┘

StateId 枚举:
  - Onchain { block:  u64, tx_index: u32 }
  - Pending { block: u64, pending_tx_hashes: Vec<H256> }

ValidationStatus 枚举:
  - Pass
  - Fail { reason: String }

索引结构: 

1. 按 block 索引 (用于 reorg 批量失效):
   BTreeMap<u64, HashMap<Address, VerifiedPoolState>>

2. 按 pool 索引 (用于查询某个 pool 的最新 state):
   HashMap<Address, BTreeMap<StateId, VerifiedPoolState>>

3. 按 pending tx 索引 (用于 pending state 的失效):
   HashMap<H256, Vec<VerifiedPoolState>>
```

#### 核心操作设计

**操作 1：插入 State**

```
输入:
  - state: VerifiedPoolState

流程:
  1. 插入到 by_block 索引: 
     by_block[state.block_number]. insert(state.pool_address, state. clone())
  
  2. 插入到 by_pool 索引: 
     by_pool[state.pool_address].insert(state.state_id, state.clone())
  
  3. 如果是 pending state，插入到 by_pending_tx 索引:
     if state.state_id is Pending: 
         for tx_hash in state.state_id.pending_tx_hashes: 
             by_pending_tx[tx_hash].push(state.clone())

并发控制:
  - 使用 RwLock 或 DashMap (高并发场景)
```

**操作 2：查询某个 Pool 在指定 Block 的最新 State**

```
输入:
  - pool_address: Address
  - block_number: u64

流程:
  1. 从 by_pool 索引查询:
     let states = by_pool.get(pool_address)?;
  
  2. 查找 <= block_number 的最新 state:
     states.range(..=StateId::onchain(block_number, u32::MAX))
           .next_back()

返回: 
  - Option<VerifiedPoolState>

时间复杂度:  O(log N)，N 为该 pool 的 state 数量
```

**操作 3：处理 Reorg**

```
输入:
  - invalid_blocks: Vec<u64>  // 被 reorg 的 block 列表

流程:
  1. 批量删除 by_block 索引中的对应 block: 
     for block in invalid_blocks: 
         if let Some(states) = by_block.remove(block):
             // 从 by_pool 索引中删除对应的 state
             for (pool_address, state) in states: 
                 by_pool.get_mut(pool_address)?.remove(&state. state_id)
  
  2. 如果涉及 pending state，也需要清理 by_pending_tx 索引

原子性保证:
  - 使用事务性删除（或全局写锁）确保不会出现部分删除的情况
```

**操作 4：清理 Pending State（当 Pending Tx 上链或失效时）**

```
输入:
  - pending_tx_hash: H256

流程:
  1. 从 by_pending_tx 索引查询:
     let states = by_pending_tx. remove(pending_tx_hash)?;
  
  2. 从 by_pool 和 by_block 索引中删除这些 states:
     for state in states:
         by_pool.get_mut(state.pool_address)?.remove(&state.state_id)
         by_block.get_mut(state. block_number)?.remove(&state.pool_address)
```

#### 持久化设计（可选）

```
问题: ExEx 重启后，Cache 中的数据会丢失

方案 A:  不持久化
  - 重启后从最新 block 重新开始观测
  - 优点: 简单
  - 缺点: 重启后需要等待新 block 才能提供数据

方案 B: 持久化到磁盘
  - 使用 RocksDB 或 Sled 存储 verified states
  - 重启后从磁盘加载最近 N 个 block 的数据
  - 优点:  重启后立即可用
  - 缺点: 增加复杂度

建议: 
  - 阶段 1: 不持久化（快速实现）
  - 阶段 2: 如果重启频繁或业务需要，再实现持久化
```

#### 关键设计点

**设计点 1：Cache 容量管理**

问题: Cache 无限增长会耗尽内存

策略: 
- 只保留最近 N 个 block 的 state（如 N=1000，约 3.5 小时）
- 定期清理过期的 state
- 使用 LRU 策略清理不常用的 pending state

**设计点 2：并发性能**

问题: 插入和查询可能并发进行

策略:
- 使用 `DashMap` (高并发 HashMap) 替代 `RwLock<HashMap>`
- 或者使用分片锁（Sharded Lock）减少锁竞争

**设计点 3：Reorg 的原子性**

问题:  Reorg 批量删除 state 时，如果删除到一半系统崩溃，可能导致数据不一致

策略:
- 使用全局写锁，确保 reorg 期间不能插入新 state
- 记录 reorg 日志，系统重启后可以恢复

### 5.6 组件 6：Pending Tx Simulator

#### 职责
- 接收观测系统发起的 pending tx 模拟请求
- 在 latest block + pending state 上模拟 tx 执行

- 调用 State Tracker/Converter/Validator 获取验证后的 state
- 返回 pending state 给观测系统


#### 工作流程

```
收到 mev_simulatePendingTx 请求

步骤 1: 准备模拟环境
  - 获取 based_on_block 的 state
  - 如果 include_prior_pending_txs 不为空，先模拟执行这些 tx
  ↓
步骤 2: 模拟执行 pending tx
  - 调用 EVM 模拟执行
  - 记录 gas_used, success
  - 获取 receipts 和 logs
  ↓
步骤 3: 识别受影响的 pool
  - 从 logs 中提取 pool 相关事件 (Sync, Swap, Mint, Burn)
  - 构建 affected_pools 列表
  ↓

  - 调用 Pool State Tracker 批量读取这些 pool 的 raw state

      block: based_on_block,
      pending_tx_hashes: include_prior_pending_txs + [pending_tx_hash],

  ↓
```
